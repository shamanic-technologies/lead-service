# Project: lead-service

Apollo/sales-lead service — buffering, deduplication, enrichment caching, and lead retrieval. All journalist functionality has been moved to journalists-service.

## Commands

- `npm test` — run all tests (Vitest)
- `npm run test:unit` — run unit tests only
- `npm run test:integration` — run integration tests only
- `npm run build` — compile TypeScript + generate OpenAPI spec
- `npm run dev` — local dev server with hot reload
- `npm run generate:openapi` — regenerate openapi.json from Zod schemas
- `npm run db:generate` — generate Drizzle migrations (⚠️ see Migrations below — do NOT use)
- `npm run db:migrate` — run Drizzle migrations
- `npm run db:push` — push schema directly (dev only)

## CI never touches a database the service uses

- **`.github/workflows/ci.yml` provisions its own `postgres:17` service container and points `LEAD_SERVICE_DATABASE_URL` at it — `secrets.LEAD_SERVICE_DATABASE_URL` must not appear in that file, on any event.** It used to: the migration step ran against the single live DSN on `pull_request`, so merely OPENING a PR moved the production schema before review, before merge, and before the code expecting the new shape shipped — and a PR later closed or reworked left its migration applied with nothing using it (#397). Production migrations come from `migrate()` on boot in `src/index.ts`, not from CI. `tests/unit/ci-workflow.test.ts` fails the build if any `${{ secrets.* }}` reference returns.
- **The CI database is EMPTY.** Anything under `tests/integration` must seed its own rows; do not write a test that passes only because production data happens to exist (that is how brand-service's suite came to fail on a clean database — brand-service#385/#387). A throwaway service container was deliberately preferred over the ephemeral Neon branch the fleet used at the time: a Neon branch was cut from the default branch, so it arrived carrying production data, and it leaked compute hours when a run failed. Neon has since been deleted and every database is one Postgres container on the Hetzner box — so there is no branch-per-CI-run option to reach for, and the rule that stands is the one above it: CI provisions its own empty `postgres:17` and never points at a database the service uses.

## Migrations — hand-author, do NOT `db:generate`

The drizzle meta snapshots (`drizzle/meta/*_snapshot.json`) stop at `0007`; migrations `0008`+ were all hand-authored. So `npm run db:generate` (`drizzle-kit generate`) has no recent snapshot to diff against and drops into an interactive prompt asking to **recreate every table** — it cannot produce a clean incremental migration. Convention: **hand-author the `.sql` file + add the journal entry to `drizzle/meta/_journal.json` yourself**. Make every statement idempotent (`DROP COLUMN IF EXISTS`, `DROP INDEX IF EXISTS`, `CREATE INDEX IF NOT EXISTS`, or `DO $$ … IF EXISTS … $$`) — see `0022`/`0023` as templates. `npm run db:migrate` (`drizzle-kit migrate`) applies the journal's `.sql` files and does NOT need the snapshots, so this works at boot.

## Architecture

- `src/schemas.ts` — Zod schemas (source of truth for validation + OpenAPI)
- `src/routes/` — Express route handlers (buffer, leads, cursor, health, stats)
- `src/middleware/auth.ts` — API key + multi-tenant header auth
- `src/lib/buffer.ts` — pullNext(), fillBufferFromSearch() buffer logic
- `src/lib/dedup.ts` — checkDelivered() (via email-gateway), markServed() deduplication
- `src/lib/email-gateway-client.ts` — Email-gateway POST /status client for delivery checks
- `src/lib/leads-registry.ts` — Global lead identity registry (leads + leadEmails tables)
- `src/lib/people-client.ts` — human-service people gateway client (provider-agnostic search/enrich via apollo OR apify; lead-service no longer calls apollo/apify directly). **Do NOT branch on provider in the consumer** (`if (provider === "apollo")`). The gateway is provider-agnostic: pass every identity field you stored (`providerPersonId` from the apollo-specific column when present, `firstName`/`lastName`/`domain` when present) and let the gateway pick the reveal path. The `(provider, providerPersonId)` pair is what disambiguates the id — `provider` qualifies it, so a generic wire field is correct; don't push per-provider routing back into lead-service. (Set 2026-06-14, v0.21.2 apollo reveal-by-person-id regression fix.)
- `src/lib/{campaign,brand}-client.ts` — campaign/brand detail fetches for search context; `src/lib/runs-client.ts` — runs-service distributed tracing. **Per-brand configuration is the data of an (org, brand) PAIR, so `orgId` is a REQUIRED argument on every `brand-client` read and `x-org-id` always goes on the wire.** A brand row is a shared global identity: any org claiming the same domain gets the same brand id, and two such orgs legitimately optimize for different goals. brand-service answers a brand claimed by exactly one org either way, but refuses to guess for a brand claimed by several — so an org-less read fails there (lead-finding stops) rather than leaking a neighbour's configuration. `buildHeaders` throws before any fetch when the org is blank; do NOT make it optional again, and do NOT substitute a plausible stand-in org, which is the leak being closed. Every call site is an org-scoped `requireOrgId` handler, so the org is always in hand.
- `src/db/schema.ts` — Drizzle ORM table definitions (PostgreSQL); `src/db/index.ts` — connection; `src/config.ts` — env config; `src/instrument.ts` — Sentry
- `tests/` — Test files (`*.test.ts`)
- `openapi.json` — Auto-generated from Zod schemas, do NOT edit manually

## Data Layering

- lead-service owns silver lead entities (`leads`, `lead_contact_methods`, `leads_organizations`, `organizations`) and per-campaign lifecycle rows (`leads_campaigns`).
- `GET /orgs/leads?view=basic` is a Gold serving projection for dashboard list views: return only the locked slim lead shape, current-employer org summary, primary email, lifecycle fields, and live delivery overlay.
- Prefer a Gold view/projection before a Gold table. Materialize only after profiling proves the joins themselves are the bottleneck; do not materialize live delivery status, and do not bake the known multi-`current=true` employment defect into stored Gold state.
- For current employer reads, never trust a bare `current=true` filter alone. Use deterministic winner selection: enriched org first, newest employment row next, stable organization id last.
- `GET /orgs/leads` brand/org scope must be ONE row per PERSON, not per campaign-membership. `leads_campaigns` is membership-grain (one row per person × campaign/serve), so brand/org reads collapse to one row per `lead_id` via global `DISTINCT ON (lead_id)` (winner = most-advanced lifecycle `served>claimed>buffered>skipped`, then latest `served_at`/`created_at`/`id`) — the kept row fires the email-keyed delivery overlay and carries the person's full engagement. Both paths dedupe: slim (`basicLeadQuery`) + full (`fetchLeadCampaignChunk`), sharing `src/lib/lead-list-query.ts`. Campaign scope (`campaignId` present) stays flat — never collapse it. The dedup is GLOBAL (a subquery), keyset-paginated over the deduped relation; never `DISTINCT ON` inside a keyset chunk (splits a person across chunk boundaries). (#320.)
- **Each lead carries its ACTIVE audience for the brand — resolved server-side, never via a client-side list fan-out.** `GET /orgs/leads` (both `view=basic` and full) returns `audience: { id, name, avatarUrl } | null` per lead. lead-service owns `leads_campaigns.audience_id` on only ~5% of rows; the rest resolve by EMAIL → active-audience membership. Both keys (tagged `audienceId` + `email`) are forwarded per chunk to human-service `POST /internal/audiences/resolve` (server-to-server, direct to `HUMAN_SERVICE_URL`, NOT the api gateway → no 100KB body cap: the resolver mounts its own 25MB parser before human-service's global 100KB `express.json()`). Request `{ orgId, brandId, audienceIds[], emails[] }` (deduped per brand group); response `{ byAudienceId, byEmail }` maps, correlated back per lead (tagged audience card preferred over email membership). human-service owns the brand-correct pick. Grouped by the scoped `brandId` when present, else the row's primary brand. Resolution runs BEFORE each chunk is written, so a resolver failure fails loud (clean 500 pre-stream / destroyed socket mid-stream) — never a silently-blank `-`. Do NOT re-introduce a browser-side membership fan-out (that 413'd the gateway — the reported bug). Client: `src/lib/audience-client.ts`. (#346, human-service#166.)
- **Timestamps read via raw `sql` come back as `Date` OR `string` — NEVER call `.toISOString()` on them directly; normalize via `toIsoTimestamp` (`src/lib/basic-leads.ts`).** postgres.js (`prepare:false`) hands a timestamptz column back as a `Date` on some paths and a raw string on others; a bare `row.servedAt.toISOString()` throws `is not a function` the moment it's a string, and on a streaming response (headers already sent) that throw destroys the socket → callers see `UND_ERR_SOCKET`, not a clean 500. Both `/orgs/leads` paths must share the helper: type raw rows `Date | string | null`, normalize at map time. The slim path (`basic-leads.ts`) always did; the full path (`fetchLeadCampaignChunk`) diverged and crashed (#328, v0.31.1). When adding any new timestamp field to a raw-`sql` query, route it through `toIsoTimestamp`, not `.toISOString()`. (#328.)
- **WRITE-side dual of the above — NEVER bind a raw JS `Date` into a raw `db.execute(sql\`...\`)` template; bind `date.toISOString()`.** A raw `sql` template passes params straight to postgres.js `Bind`, which (unlike drizzle's typed insert builder `db.insert().values({ col: new Date() })`, or postgres.js's own tagged template) does NOT serialize a `Date` — it calls `Buffer.byteLength(value)` and throws `TypeError [ERR_INVALID_ARG_TYPE]: The "string" argument must be of type string ... Received an instance of Date` at Bind time. This is a CLIENT-side throw, so it is invisible to raw-SQL / `EXECUTE ... USING` tests run directly against the DB (the query text is fine; the driver never gets to send it) — the DB looks fully healthy while every request 500s. The ISO string casts to the timestamptz column. This 500'd EVERY `POST /public/conversions` conversion event since the beta ingest — `conversion_events` had 0 real rows for weeks (only `ping`, which uses SQL `now()` with no Date param, worked). When writing via raw `db.execute(sql\`...\`)`, bind primitives only (string/number/null/`.toISOString()`); reach for `db.insert()`/`db.update()` typed builders if you want a `Date` serialized for you. (#357/#370, v0.39.0.)
- **A person is ONE identity, keyed EMAIL-FIRST — never serve a lead whose email is not registered.** `idx_lcm_channel_value` makes "one email = one lead" a hard invariant, and the read path keys the email-gateway delivery overlay on the lead's REGISTERED email. So a served lead with no email contact method can NEVER resolve contacted/sent/delivered: it is invisible in the dashboard funnel, absent from outreach counts, and absent from features-service conversion attribution — paid-for emails missing from every cost-per-outcome denominator. `upsertLeadFromPerson` therefore resolves identity as (1) the lead that already owns `person.email`, (2) the lead carrying `person.providerPersonId`, (3) a fresh row — email BEFORE provider id, because provider ids churn (a re-crawl mints a new id for the same human) while a registered email cannot move. `registerServedEmail` then guarantees the returned lead owns the email (re-resolving on the concurrent-serve race) and fails loud if it can't — do NOT restore the old warn-and-serve-anyway branch, do NOT weaken the global uniqueness, and do NOT make the read path fall back to `leads.metadata->>'email'` (that hides an absent record and leaves every other consumer wrong). Historical rows repaired by `scripts/repair-served-lead-emails.ts` (dry-runnable, idempotent, `leads_campaigns.repointed_from_lead_id` records the pre-repair attribution). (#393.)
- **A serve that was paid for and never contacted is un-consumed by ARCHIVING the `leads_campaigns` row into `requeued_serves` and DELETING it — never by flipping its status.** `idx_lc_lead_campaign` is unique on `(lead_id, campaign_id)` regardless of status, so a surviving row of ANY status makes the serve path's `ON CONFLICT DO NOTHING` keep the stale row (old run ids, old `served_at`) if the person is re-served to the campaign that lost them: the re-serve is mis-attributed and the person reads as long-since contacted while the vendor has just received them. `scripts/requeue-uncontacted-serves.ts` (one-time, `--dry-run`, idempotent, reversible from `row_snapshot`, tagged `reason`) is the only writer; the serve path never touches that table. Contact evidence is NEVER inferred from "the send failed": it comes from the service that submitted to the vendor, in two fail-closed gates — `scripts/sql/exclude-vendor-contacted.sql` drops anyone holding an `instantly_campaigns` row (cross-brand/cross-org, deliberately conservative, in SQL because only instantly-service's own DB can answer it), then the script asks email-gateway `POST /orgs/status` at BRAND scope for the per-brand answer. **The no-re-serve guarantee itself is human-service's `brand_suppressions` (keyed `(org, brand, email_norm)`, 3-month window) — lead-service does not own it and must not write it; this repair only makes the lifecycle row correct so a released person can be re-served.** Do NOT generalise any of this into a recurring sweep, retry loop, or detector: the producer bug (instantly-service#570/#573) is fixed and the affected set is closed. (#406.)
- **A campaign-scoped read answers for the campaign IDENTITY, not the single stored campaign row.** A campaign as the customer knows it is `(org, brand, sales funnel, acquisition channel)` — campaign-service's own key (its migration 0044 `uniq_campaigns_org_brand_funnel_channel`). campaign-service used to mint a NEW row on every workflow switch, so one real campaign exists in storage as dozens of rows, one alive and the rest stopped; product surfaces show one line per identity, and features-service already totals that way. So `GET /orgs/leads?campaignId=` and `GET /orgs/stats?campaignId=` resolve the family first (`src/lib/campaign-identity.ts` — the same grouping features-service uses — via `resolveCampaignFamily`, an ORG-scoped read of campaign-service `/campaigns`) and filter on `campaign_id = ANY(family)`. Three consequences that are load-bearing, not incidental: (1) a MULTI-member scope dedupes to one row per person exactly like brand scope, else a campaign count exceeds the brand count for the same people; (2) delivery evidence is keyed by email-gateway on the campaign that SENT, so a multi-member scope asks in BRAND mode and reads the identity's members out of `byCampaign` (`flattenFamilyStatus`) — asking in campaign mode for the live id alone reports a paid-for, contacted person as never contacted, which is the same bug in the other direction; (3) the read is ORG-scoped because campaign-service's `brandId` filter matches the legacy `brand_ids` ARRAY, and a member carrying the brand only in `brand_id` would drop out — a PARTIAL family is worse than not widening. Resolution failing falls back to the single requested row with a loud log, never to a partial family and never to the brand. Never rewrite, repoint or delete stored rows to "fix" this: every campaign id keeps answering, only what a campaign-scoped read TOTALS changed. Do NOT add a query param for callers to opt in — the existing scope means the identity. (#410.)
- **`GET /orgs/leads` answers for the ACTIONABLE population by default — `buffered,claimed,served`, NOT `skipped` — and a caller widens it with `?status=`.** The delivery overlay is only fetched for `status = 'served'` rows, so a `skipped` row carries no engagement evidence by construction: every one of its status fields is false/null, no engagement-bucketed view can reach it (the dashboard's tabs are all engagement steps), and features-service's revenue engine drops it (it keeps only persons with EV > 0 or a delivery milestone). For one real brand it was 53,760 of 53,777 rows — ~82% of a 102 MB slim body, on an endpoint the dashboard polls every 30s. `status` takes a comma-separated list of the four lifecycle statuses or `all`; an unknown value is a 400, never a silent fallback (`parseLeadStatusFilter`, `src/lib/lead-list-query.ts`). The predicate is applied INSIDE the dedup subquery as well as on the outer query, so the winning membership row per person is chosen among the statuses the caller asked for. Do NOT re-widen the default to "everything" to fix a consumer that lost rows — teach that consumer to ask (the admin app asks for `all`, which is why it still has a Skipped tab). Narrowing by lifecycle is a different lever from bounding how much comes back — see the next bullet. (#414.)
- **`GET /orgs/leads` honours a caller-supplied `limit`, and no `limit` still means the WHOLE population.** The bound is expressed as `limit` + an opaque `cursor` (its positional twin `offset` is accepted for the gateway's published contract), and the response carries `nextCursor`: the position to resume from, or null when the response reached the end. The walk is keyset over `(created_at, id)` — `id` is unique, so that order is TOTAL and a walk visits every row exactly once, no gaps, no repeats, even while new leads are being written (they append at the end). There is deliberately NO server-imposed ceiling: the staff console legitimately reads a whole 57k-row brand, so a cap the caller cannot control would be a different bug, and an absent `limit` keeps the slim path on its single server-side `.cursor()` query, byte for byte as before. A bound arrives at the DATABASE (`LIMIT`/`OFFSET` on the outer query, chunk size clamped to what is still owed): a `limit=50` read hydrates, delivery-overlays, audience-resolves and serializes 50 rows, not the brand's population — that is why the common case is cheap rather than merely capped. Every unparseable bound (`limit=0`, `limit=abc`, `offset=-1`, a cursor this endpoint did not issue, `cursor` AND `offset` together) is a 400 before any work starts. Do NOT make any of them a silent fallback: this endpoint accepted `limit` and dropped it for months, answering 112 MB with a 200 to callers asking for 50 rows, and a silently-ignored bound is invisible by construction — nothing anywhere goes red. Route tests must assert the bound reaches the SQL, not just that the array is short (`tests/unit/lead-list-walk.test.ts` mocks `sql` so it honours LIMIT/OFFSET/keyset; a mock that returns a fixed slice would pass a handler that drops the bound). **The cursor's `createdAt` is `Date | string` and normalizes at ENCODE time — the `toIsoTimestamp` hazard above applies to it, because a cursor is built straight off a raw `sql` row: typing it `Date` and calling `.toISOString()` shipped green, then threw `is not a function` on the first production request, mid-stream, which destroys the socket instead of producing a clean 500. Test fixtures for these paths must use a raw timestamp STRING (`"2026-01-01 00:00:00+00"`), not `new Date(...)`; a Date fixture passes a handler that is broken in production. **Its write-side twin bit on the very next request: a DECODED cursor holds a real `Date`, and binding that into the keyset predicate throws postgres.js's `ERR_INVALID_ARG_TYPE ... Received an instance of Date` at Bind time — so the timestamp is bound through `leadCursorTimestampParam` (ISO string), never raw. The `sql` mocks in `tests/unit/lead-list-walk.test.ts` / `leads-route-page.test.ts` carry an `assertBindable` that throws on a `Date` param exactly like Bind does; without it both halves of this ship green.** **The position itself is `created_at::text`, selected as a SECOND column alongside the typed one and carried through the cursor verbatim: `timestamptz` holds MICROseconds and a JS `Date` holds milliseconds, so rendering a position through a Date floors it and the next page re-reads everything inside the dropped microseconds — a full production walk of a 57k-row brand returned 57,737 rows for 57,622 people (115 repeats, no gaps) before the text column existed. Never build a cursor from the typed `createdAt`.** (#417, v0.52.1–v0.52.3.)
- **Raw-`sql` route tests that mock `db.execute` do NOT exercise postgres.js `Bind` — a handler that binds an unserializable param (a raw `Date`) still ships GREEN.** The plain `vi.fn()` mock returns rows without ever encoding params, so the Bind-time throw above never fires in tests. Any test asserting a raw-`sql` write handler returns 200 MUST also assert the compiled params are Bind-serializable (no `Date` instance) — see the `assertBindable` Bind-faithful mock in `tests/unit/conversions-routes.test.ts`, which throws on a raw `Date` exactly like prod. Without it a 100%-broken handler passes CI. (#370.)

## Boot — the port opens BEFORE migrations, and traffic is gated until they finish

- **`app.listen()` runs FIRST; `migrate()` runs behind it.** This was learned on Neon, whose computes suspended after inactivity: a deploy landing on a cold compute spent its whole startup budget on the first connection, so the port never opened inside Railway's 30s healthcheck window (`1/1 replicas never became healthy!`, with no application output at all — not even "Migrations complete" — because the stall happens before any logging), or the connection was refused mid-resume and the old `.catch(process.exit(1))` turned it into a restart loop. Neon and Railway are both gone; the failure SHAPE is not. Any moment the database is not ready to accept a connection right now — the Postgres container restarting, the box rebooting, a deploy restarting things underneath — reproduces it exactly, and `deploy.sh`'s health check will roll the release back for a port that never opened. The failure has nothing to do with the code being deployed, which is what makes it expensive: it reads as a flaky deploy, you retry, the DB is up by then, it passes. Do NOT move migrations back in front of `listen()`, and do NOT add pre-listen startup work (`registerProviders()` used to be there too — it now runs after readiness, non-fatal, because publishing metadata to key-service is not schema and a key-service outage must not hold the service at 503).
- **Opening the port early is only safe because `requireBootReady` (`src/middleware/readiness.ts`) 503s every route until migrations complete.** The service must never serve a request against a schema its code does not expect. `/health` is mounted BEFORE the gate; everything else after it. Keep that order when adding routers.
- **`/health` is boot-state-aware and must NOT ping the DB while `starting`.** Three states (`src/lib/boot-state.ts`): `starting` → 200 `{status:"starting",migrations:"pending"}` with no DB access (a database not yet accepting connections would otherwise fail the ping and take the deploy down — the exact bug, originally a Neon compute mid-resume); `ready` → the usual `SELECT 1` ping; `failed` → 503 naming the migration error, so the deploy's health check fails loudly and `deploy.sh` rolls back to the previous build. On migration failure the process deliberately stays ALIVE rather than `process.exit(1)` — exiting produces a restart loop that shreds the logs carrying the reason.
- **Migration retry is connect-phase ONLY (`withConnectRetry`, `src/lib/db-retry.ts`).** A rejected connection never dispatched a statement, so retrying it cannot half-apply a migration; a real migration error (bad SQL, failed constraint) is NOT retried and surfaces on the first throw. Budget ~65s, front-loaded (250ms → 8s) — sized to cover a Neon resume many times over when it was written, and it comfortably covers a Postgres container coming back up. Transient detection walks `cause` chains and `AggregateError.errors` (Node-20 happy-eyeballs produces one sub-error per candidate address) and matches driver codes, SQLSTATE class 08, `57P03` (`cannot_connect_now` — Neon returned it while resuming, and Postgres returns it while still starting up), and the code-less pool-acquire message `timeout exceeded when trying to connect`.
- **Do NOT "fix" cold starts with postgres.js connection options.** `connect_timeout: 30` is already the postgres.js default (`postgres/src/index.js`), so setting it is a no-op; `idle_timeout` defaults to `null` (idle connections are never closed), so setting a value makes them close and buys a fresh TCP+TLS handshake on the next request — that advice is correct for node-postgres, whose default really is an aggressive 10s teardown, and was mis-transplanted. Both were tried and reverted in brand-service#389. The one connection-layer setting kept here is `net.setDefaultAutoSelectFamilyAttemptTimeout(5_000)` in `src/db/index.ts`, which widens Node 20's 250ms per-candidate happy-eyeballs budget so the first connection to a database that is not yet ready is not aborted before it is answered.
- **A test file that `vi.mock`s `src/db/index.js` MUST `vi.resetModules()` between cases.** Without it the mocked module registry leaks into LATER test files in the same worker, and the symptom lands nowhere near the cause: `tests/unit/stats-persona-attribution.test.ts` hung to a 5s timeout, deterministically, because `health.test.ts` ran before it without the reset. Import the boot-state singleton through the same fresh registry as the route under test (a static top-level import binds to a different instance after `resetModules` and silently stops driving it) — see `tests/unit/health.test.ts`.

## Outbound-call resilience & route error handling

- **ALL outbound calls to runs-service go through `fetchWithRetry` (`src/lib/fetch-retry.ts`), never raw `fetch`.** runs-service used to sit behind Neon scale-to-zero, so the first call after an idle suspend landed mid-wake (~1-7s resume) and aborted the old raw `fetch(..., { signal: AbortSignal.timeout(5_000) })` with a `TimeoutError`/socket-reset. Scale-to-zero is gone, the failure is not: a sibling that is restarting, redeploying, or coming back with the box still refuses or resets the first connection the same way. `runs-client.ts` + `trace-event.ts` now use `fetchWithRetry` (connect-phase retry on `ECONNRESET`/`ECONNREFUSED` — write-safe, request never reached the server) + a 30s timeout (fleet norm; 5s was the outlier that couldn't fit a slow first connect). Any NEW runs-client function (or any client to a sibling service on a fail-loud path) must use `fetchWithRetry`, not raw `fetch`. (#390, v0.44.1.)
- **An `async` Express route handler's throw does NOT become a 500 automatically (Express 4) — it rejects the handler's promise, which Express ignores → `unhandledRejection` + the caller's socket HANGS with no response.** So any `await` in a route handler that can throw MUST be inside a `try` that `return res.status(5xx)`s. The trap: work done BEFORE the main `try` block (idempotency lookup, in-flight guard, `createRun`) is unguarded — a runs-service outage there escaped as an unhandled rejection instead of a clean 500. `POST /orgs/buffer/next` wraps its entire pre-serve block. When adding pre-`try` setup awaits to a route, extend the guard. Route tests must assert 500-on-throw with NO error middleware mounted (Express 4 wouldn't forward the async rejection to it anyway) — see `tests/unit/buffer-route.test.ts`. (#390, v0.44.1.)

## API Design Rules

- **Minimal request body.** Everything that workflow-service auto-injects as headers (`x-org-id`, `x-user-id`, `x-run-id`, `x-campaign-id`, `x-brand-id`, `x-workflow-slug`, `x-feature-slug`) MUST be read from headers, never duplicated in the body.
- **No `.default()` on Zod fields.** If a field is needed, make it required. A missing field is a 400, not a silent default.
- **No optional "convenience" fields.** If the service can fetch data internally (campaign context from campaign-service, brand fields from brand-service), do NOT accept it as a body parameter. Fetch it yourself. **This extends to identity HEADERS, not just body fields: a header carrying a producer-owned attribute that is *derivable* from an entity already identified by another header must be fetched, not required.** The `goal` (signup|meetingBooked|purchase) is a brand attribute (brand-service `brands.currentGoal`), derivable from `x-brand-id` via `GET /internal/brands/:brandId/runtime-context` — so lead-service fetches it inside buffer/next, never requires `x-goal` (v0.25). Carve-out: headers that ARE the request's identity (`x-org-id`, `x-campaign-id`, `x-brand-id`, `x-run-id`, `x-audience-id`) stay headers — they name *which* entity, they are not derivable attributes OF it.
- **Audience selection is campaign-owned — lead-service NEVER re-ranks/re-selects.** campaign-service decides the priority audience per run (`internal.ts` → features persona-stats) and propagates it as `x-audience-id` to every downstream DAG node. `buffer/next` serves the audience named by `x-audience-id` (`req.audienceId`) directly; no `x-audience-id` ⟹ clean `found:false` (campaign selected none). Do NOT re-introduce a features-service `persona-stats`/`getTopAudienceId` call in lead-service — that duplicated, divergent selection let an uncommitted audience be picked and 422 at serve-next (v0.26.1 removed it). Serveability (audience has a committed provider) is enforced upstream in human-service; lead-service treats serve-next 422 "no committed provider" as `found:false` (reason `audience_not_serveable`), never a 500.
- **Idempotency is internal.** Use `x-run-id` as the idempotency key. Never expose idempotency keys in the API surface.
