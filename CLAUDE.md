# Project: lead-service

**The GitHub repo is `sales-lead-service`; the Hetzner box clones it as `/root/distribute/repos/lead-service`** (and the container is `distribute-lead-service-1`, the env file `env/lead-service.env`). A post-deploy poll built on the repo name reads a path that does not exist, which looks exactly like a deploy that has not landed — cost a 10-minute exhausted poll on v0.65.1 while `deploy.log` already said `lead-service: healthy on 28307cd1`.

Apollo/sales-lead service — buffering, deduplication, enrichment caching, and lead retrieval. All journalist functionality has been moved to journalists-service.

## CI never touches a database the service uses

- **`.github/workflows/ci.yml` provisions its own `postgres:17` service container and points `LEAD_SERVICE_DATABASE_URL` at it — `secrets.LEAD_SERVICE_DATABASE_URL` must not appear in that file, on any event.** It used to: the migration step ran against the single live DSN on `pull_request`, so merely OPENING a PR moved the production schema before review, before merge, and before the code expecting the new shape shipped — and a PR later closed or reworked left its migration applied with nothing using it (#397). Production migrations come from `migrate()` on boot in `src/index.ts`, not from CI. `tests/unit/ci-workflow.test.ts` fails the build if any `${{ secrets.* }}` reference returns.
- **The CI database is EMPTY.** Anything under `tests/integration` must seed its own rows; do not write a test that passes only because production data happens to exist (that is how brand-service's suite came to fail on a clean database — brand-service#385/#387). A throwaway service container was deliberately preferred over the ephemeral Neon branch the fleet used at the time: a Neon branch was cut from the default branch, so it arrived carrying production data, and it leaked compute hours when a run failed. Neon has since been deleted and every database is one Postgres container on the Hetzner box — so there is no branch-per-CI-run option to reach for, and the rule that stands is the one above it: CI provisions its own empty `postgres:17` and never points at a database the service uses.

## Migrations — hand-author, do NOT `db:generate`

The drizzle meta snapshots (`drizzle/meta/*_snapshot.json`) stop at `0007`; migrations `0008`+ were all hand-authored. So `npm run db:generate` (`drizzle-kit generate`) has no recent snapshot to diff against and drops into an interactive prompt asking to **recreate every table** — it cannot produce a clean incremental migration. Convention: **hand-author the `.sql` file + add the journal entry to `drizzle/meta/_journal.json` yourself**. Make every statement idempotent (`DROP COLUMN IF EXISTS`, `DROP INDEX IF EXISTS`, `CREATE INDEX IF NOT EXISTS`, or `DO $$ … IF EXISTS … $$`) — see `0022`/`0023` as templates. `npm run db:migrate` (`drizzle-kit migrate`) applies the journal's `.sql` files and does NOT need the snapshots, so this works at boot.

## Architecture

- `src/schemas.ts` — Zod schemas (source of truth for validation + OpenAPI)
- `src/routes/` — Express route handlers (buffer, leads, cursor, health, stats)
- `src/middleware/auth.ts` — API key + multi-tenant header auth
- `src/lib/buffer.ts` — pullNext(), fillBufferFromSearch() buffer logic
- `src/lib/dedup.ts` — checkDelivered() (via email-gateway), markServed() deduplication
- `src/lib/email-gateway-client.ts` — Email-gateway POST /status client for delivery checks
- `src/lib/leads-registry.ts` — Global lead identity registry (leads + leadEmails tables)
- `src/lib/people-client.ts` — human-service people gateway client (provider-agnostic search/enrich via apollo OR apify; lead-service no longer calls apollo/apify directly). **Do NOT branch on provider in the consumer** (`if (provider === "apollo")`). The gateway is provider-agnostic: pass every identity field you stored (`providerPersonId` from the apollo-specific column when present, `firstName`/`lastName`/`domain` when present) and let the gateway pick the reveal path. The `(provider, providerPersonId)` pair is what disambiguates the id — `provider` qualifies it, so a generic wire field is correct; don't push per-provider routing back into lead-service. (Set 2026-06-14, v0.21.2 apollo reveal-by-person-id regression fix.)
- `src/lib/{campaign,brand}-client.ts` — campaign/brand detail fetches for search context; `src/lib/runs-client.ts` — runs-service distributed tracing. **Per-brand configuration is the data of an (org, brand) PAIR, so `orgId` is a REQUIRED argument on every `brand-client` read and `x-org-id` always goes on the wire.** A brand row is a shared global identity: any org claiming the same domain gets the same brand id, and two such orgs legitimately optimize for different goals. brand-service answers a brand claimed by exactly one org either way, but refuses to guess for a brand claimed by several — so an org-less read fails there (lead-finding stops) rather than leaking a neighbour's configuration. `buildHeaders` throws before any fetch when the org is blank; do NOT make it optional again, and do NOT substitute a plausible stand-in org, which is the leak being closed. Every call site is an org-scoped `requireOrgId` handler, so the org is always in hand.
- `src/db/schema.ts` — Drizzle ORM table definitions (PostgreSQL); `src/db/index.ts` — connection; `src/config.ts` — env config; `src/instrument.ts` — Sentry
- `tests/` — Test files (`*.test.ts`)
- `openapi.json` — Auto-generated from Zod schemas, do NOT edit manually

## Data Layering

- lead-service owns silver lead entities (`leads`, `lead_contact_methods`, `leads_organizations`, `organizations`) and per-campaign lifecycle rows (`leads_campaigns`).
- `GET /orgs/leads?view=basic` is a Gold serving projection for dashboard list views: return only the locked slim lead shape, current-employer org summary, primary email, lifecycle fields, and live delivery overlay.
- Prefer a Gold view/projection before a Gold table. Materialize only after profiling proves the joins themselves are the bottleneck; do not materialize live delivery status, and do not bake the known multi-`current=true` employment defect into stored Gold state.
- For current employer reads, never trust a bare `current=true` filter alone. Use deterministic winner selection: enriched org first, newest employment row next, stable organization id last.
- `GET /orgs/leads` brand/org scope must be ONE row per PERSON, not per campaign-membership. `leads_campaigns` is membership-grain (one row per person × campaign/serve), so brand/org reads collapse to one row per `lead_id` via global `DISTINCT ON (lead_id)` (winner = most-advanced lifecycle `served>claimed>buffered>skipped`, then latest `served_at`/`created_at`/`id`) — the kept row fires the email-keyed delivery overlay and carries the person's full engagement. Both paths dedupe: slim (`basicLeadQuery`) + full (`fetchLeadCampaignChunk`), sharing `src/lib/lead-list-query.ts`. Campaign scope (`campaignId` present) stays flat — never collapse it. The dedup is GLOBAL (a subquery), keyset-paginated over the deduped relation; never `DISTINCT ON` inside a keyset chunk (splits a person across chunk boundaries). (#320.)
- **Each lead carries its ACTIVE audience for the brand — resolved server-side, never via a client-side list fan-out.** `GET /orgs/leads` (both `view=basic` and full) returns `audience: { id, name, avatarUrl } | null` per lead. lead-service owns `leads_campaigns.audience_id` on only ~5% of rows; the rest resolve by EMAIL → active-audience membership. Both keys (tagged `audienceId` + `email`) are forwarded per chunk to human-service `POST /internal/audiences/resolve` (server-to-server, direct to `HUMAN_SERVICE_URL`, NOT the api gateway → no 100KB body cap: the resolver mounts its own 25MB parser before human-service's global 100KB `express.json()`). Request `{ orgId, brandId, audienceIds[], emails[] }` (deduped per brand group); response `{ byAudienceId, byEmail }` maps, correlated back per lead (tagged audience card preferred over email membership). human-service owns the brand-correct pick. Grouped by the scoped `brandId` when present, else the row's primary brand. Resolution runs BEFORE each chunk is written, so a resolver failure fails loud (clean 500 pre-stream / destroyed socket mid-stream) — never a silently-blank `-`. Do NOT re-introduce a browser-side membership fan-out (that 413'd the gateway — the reported bug). Client: `src/lib/audience-client.ts`. (#346, human-service#166.)
- **Timestamps read via raw `sql` come back as `Date` OR `string` — NEVER call `.toISOString()` on them directly; normalize via `toIsoTimestamp` (`src/lib/basic-leads.ts`).** postgres.js (`prepare:false`) hands a timestamptz column back as a `Date` on some paths and a raw string on others; a bare `row.servedAt.toISOString()` throws `is not a function` the moment it's a string, and on a streaming response (headers already sent) that throw destroys the socket → callers see `UND_ERR_SOCKET`, not a clean 500. Both `/orgs/leads` paths must share the helper: type raw rows `Date | string | null`, normalize at map time. The slim path (`basic-leads.ts`) always did; the full path (`fetchLeadCampaignChunk`) diverged and crashed (#328, v0.31.1). When adding any new timestamp field to a raw-`sql` query, route it through `toIsoTimestamp`, not `.toISOString()`. (#328.)
- **WRITE-side dual of the above — NEVER bind a raw JS `Date` into a raw `db.execute(sql\`...\`)` template; bind `date.toISOString()`.** A raw `sql` template passes params straight to postgres.js `Bind`, which (unlike drizzle's typed insert builder `db.insert().values({ col: new Date() })`, or postgres.js's own tagged template) does NOT serialize a `Date` — it calls `Buffer.byteLength(value)` and throws `TypeError [ERR_INVALID_ARG_TYPE]: The "string" argument must be of type string ... Received an instance of Date` at Bind time. This is a CLIENT-side throw, so it is invisible to raw-SQL / `EXECUTE ... USING` tests run directly against the DB (the query text is fine; the driver never gets to send it) — the DB looks fully healthy while every request 500s. The ISO string casts to the timestamptz column. This 500'd EVERY `POST /public/conversions` conversion event since the beta ingest — `conversion_events` had 0 real rows for weeks (only `ping`, which uses SQL `now()` with no Date param, worked). When writing via raw `db.execute(sql\`...\`)`, bind primitives only (string/number/null/`.toISOString()`); reach for `db.insert()`/`db.update()` typed builders if you want a `Date` serialized for you. (#357/#370, v0.39.0.)
- **A person is ONE identity, keyed EMAIL-FIRST — never serve a lead whose email is not registered.** `idx_lcm_channel_value` makes "one email = one lead" a hard invariant, and the read path keys the email-gateway delivery overlay on the lead's REGISTERED email. So a served lead with no email contact method can NEVER resolve contacted/sent/delivered: it is invisible in the dashboard funnel, absent from outreach counts, and absent from features-service conversion attribution — paid-for emails missing from every cost-per-outcome denominator. `upsertLeadFromPerson` therefore resolves identity as (1) the lead that already owns `person.email`, (2) the lead carrying `person.providerPersonId`, (3) a fresh row — email BEFORE provider id, because provider ids churn (a re-crawl mints a new id for the same human) while a registered email cannot move. `registerServedEmail` then guarantees the returned lead owns the email (re-resolving on the concurrent-serve race) and fails loud if it can't — do NOT restore the old warn-and-serve-anyway branch, do NOT weaken the global uniqueness, and do NOT make the read path fall back to `leads.metadata->>'email'` (that hides an absent record and leaves every other consumer wrong). Historical rows repaired by `scripts/repair-served-lead-emails.ts` (dry-runnable, idempotent, `leads_campaigns.repointed_from_lead_id` records the pre-repair attribution). (#393.)
- **A serve that was paid for and never contacted is un-consumed by ARCHIVING the `leads_campaigns` row into `requeued_serves` and DELETING it — never by flipping its status.** `idx_lc_lead_campaign` is unique on `(lead_id, campaign_id)` regardless of status, so a surviving row of ANY status makes the serve path's `ON CONFLICT DO NOTHING` keep the stale row (old run ids, old `served_at`) if the person is re-served to the campaign that lost them: the re-serve is mis-attributed and the person reads as long-since contacted while the vendor has just received them. `scripts/requeue-uncontacted-serves.ts` (one-time, `--dry-run`, idempotent, reversible from `row_snapshot`, tagged `reason`) is the only writer; the serve path never touches that table. Contact evidence is NEVER inferred from "the send failed": it comes from the service that submitted to the vendor, in two fail-closed gates — `scripts/sql/exclude-vendor-contacted.sql` drops anyone holding an `instantly_campaigns` row (cross-brand/cross-org, deliberately conservative, in SQL because only instantly-service's own DB can answer it), then the script asks email-gateway `POST /orgs/status` at BRAND scope for the per-brand answer. **The no-re-serve guarantee itself is human-service's `brand_suppressions` (keyed `(org, brand, email_norm)`, 3-month window) — lead-service does not own it and must not write it; this repair only makes the lifecycle row correct so a released person can be re-served.** Do NOT generalise any of this into a recurring sweep, retry loop, or detector: the producer bug (instantly-service#570/#573) is fixed and the affected set is closed. (#406.)
- **A lead's `timezone` comes out of the stored enrichment or it stays NULL — never from a country, a city, or any other heuristic.** Apollo returns `time_zone` on the ENRICHMENT response only (never on search) and has since February 2026; the reader that persists it landed in August, so 86,738 leads carried a null timezone and were refused at the send step after we had already paid to find, enrich and write to them. `scripts/backfill-lead-timezone.ts` (one-time, `--dry-run`, idempotent via `timezone IS NULL`, reversible from the `--report` id list) fills them from `scripts/sql/apollo-lead-timezones.sql`, a plain SELECT against apollo-service's own `apollo_people_enrichments`. **That SQL step is what makes the repair provably credit-free**: apollo-service `POST /enrich` BUYS on a cache miss, and its cache hit additionally requires `email IS NOT NULL AND email_status = 'verified' AND created_at > 12 months ago`, so driving 28k rows through it would have re-purchased everyone those predicates exclude — the value is already stored, so it is read, not re-bought. The query must read `COALESCE(time_zone, response_raw->>'time_zone')`: apollo-service promotes the typed column only for enrichments written after its own reader landed (43,966 raw vs 17,317 typed in prod), and the typed column alone recovers ~17k people instead of ~28k. A lead with no city and no country (55,349 of them) keeps a null timezone — that is the honest answer and the send chain accepts it. **Match a large caller-supplied key set with `col = ANY(${ids}::text[])`, never by joining against `unnest(...)`**: Postgres hashes the array once and probes it per row, while the join/`EXISTS` form plans as a nested loop over a function scan — 86,738 leads × 41,761 known people, which never returned (the same count comes back in under a second as an array probe). Wrap it in `coalesce(..., false)` when the column is nullable, because the comparison is NULL for those rows and a NULL drops them out of BOTH the matched bucket and its complement. Do NOT generalise this into a recurring sweep: the live path persists the timezone at serve, and the affected set is closed. (#428.)
- **A campaign-scoped read answers for the campaign IDENTITY, not the single stored campaign row.** A campaign as the customer knows it is `(org, brand, sales funnel, acquisition channel)` — campaign-service's own key (its migration 0044 `uniq_campaigns_org_brand_funnel_channel`). campaign-service used to mint a NEW row on every workflow switch, so one real campaign exists in storage as dozens of rows, one alive and the rest stopped; product surfaces show one line per identity, and features-service already totals that way. So `GET /orgs/leads?campaignId=` and `GET /orgs/stats?campaignId=` resolve the family first (`src/lib/campaign-identity.ts` — the same grouping features-service uses — via `resolveCampaignFamily`, an ORG-scoped read of campaign-service `/campaigns`) and filter on `campaign_id = ANY(family)`. Three consequences that are load-bearing, not incidental: (1) a MULTI-member scope dedupes to one row per person exactly like brand scope, else a campaign count exceeds the brand count for the same people; (2) delivery evidence is keyed by email-gateway on the campaign that SENT, so a multi-member scope asks in BRAND mode and reads the identity's members out of `byCampaign` (`flattenFamilyStatus`) — asking in campaign mode for the live id alone reports a paid-for, contacted person as never contacted, which is the same bug in the other direction; (3) the read is ORG-scoped because campaign-service's `brandId` filter matches the legacy `brand_ids` ARRAY, and a member carrying the brand only in `brand_id` would drop out — a PARTIAL family is worse than not widening. Resolution failing falls back to the single requested row with a loud log, never to a partial family and never to the brand. Never rewrite, repoint or delete stored rows to "fix" this: every campaign id keeps answering, only what a campaign-scoped read TOTALS changed. Do NOT add a query param for callers to opt in — the existing scope means the identity. (#410.)
- **`GET /orgs/leads` answers for the ACTIONABLE population by default — `buffered,claimed,served`, NOT `skipped` — and a caller widens it with `?status=`.** The delivery overlay is only fetched for `status = 'served'` rows, so a `skipped` row carries no engagement evidence by construction: every one of its status fields is false/null, no engagement-bucketed view can reach it (the dashboard's tabs are all engagement steps), and features-service's revenue engine drops it (it keeps only persons with EV > 0 or a delivery milestone). For one real brand it was 53,760 of 53,777 rows — ~82% of a 102 MB slim body, on an endpoint the dashboard polls every 30s. `status` takes a comma-separated list of the four lifecycle statuses or `all`; an unknown value is a 400, never a silent fallback (`parseLeadStatusFilter`, `src/lib/lead-list-query.ts`). The predicate is applied INSIDE the dedup subquery as well as on the outer query, so the winning membership row per person is chosen among the statuses the caller asked for. Do NOT re-widen the default to "everything" to fix a consumer that lost rows — teach that consumer to ask (the admin app asks for `all`, which is why it still has a Skipped tab). Narrowing by lifecycle is a different lever from bounding how much comes back — see the next bullet. (#414.)
- **`GET /orgs/leads` honours a caller-supplied `limit`, and no `limit` still means the WHOLE population.** The bound is expressed as `limit` + an opaque `cursor` (its positional twin `offset` is accepted for the gateway's published contract), and the response carries `nextCursor`: the position to resume from, or null when the response reached the end. The walk is keyset over `(created_at, id)` — `id` is unique, so that order is TOTAL and a walk visits every row exactly once, no gaps, no repeats, even while new leads are being written (they append at the end). There is deliberately NO server-imposed ceiling: the staff console legitimately reads a whole 57k-row brand, so a cap the caller cannot control would be a different bug, and an absent `limit` keeps the slim path on its single server-side `.cursor()` query, byte for byte as before. A bound arrives at the DATABASE (`LIMIT`/`OFFSET` on the outer query, chunk size clamped to what is still owed): a `limit=50` read hydrates, delivery-overlays, audience-resolves and serializes 50 rows, not the brand's population — that is why the common case is cheap rather than merely capped. Every unparseable bound (`limit=0`, `limit=abc`, `offset=-1`, a cursor this endpoint did not issue, `cursor` AND `offset` together) is a 400 before any work starts. Do NOT make any of them a silent fallback: this endpoint accepted `limit` and dropped it for months, answering 112 MB with a 200 to callers asking for 50 rows, and a silently-ignored bound is invisible by construction — nothing anywhere goes red. Route tests must assert the bound reaches the SQL, not just that the array is short (`tests/unit/lead-list-walk.test.ts` mocks `sql` so it honours LIMIT/OFFSET/keyset; a mock that returns a fixed slice would pass a handler that drops the bound). **The cursor's `createdAt` is `Date | string` and normalizes at ENCODE time — the `toIsoTimestamp` hazard above applies to it, because a cursor is built straight off a raw `sql` row: typing it `Date` and calling `.toISOString()` shipped green, then threw `is not a function` on the first production request, mid-stream, which destroys the socket instead of producing a clean 500. Test fixtures for these paths must use a raw timestamp STRING (`"2026-01-01 00:00:00+00"`), not `new Date(...)`; a Date fixture passes a handler that is broken in production. **Its write-side twin bit on the very next request: a DECODED cursor holds a real `Date`, and binding that into the keyset predicate throws postgres.js's `ERR_INVALID_ARG_TYPE ... Received an instance of Date` at Bind time — so the timestamp is bound through `leadCursorTimestampParam` (ISO string), never raw. The `sql` mocks in `tests/unit/lead-list-walk.test.ts` / `leads-route-page.test.ts` carry an `assertBindable` that throws on a `Date` param exactly like Bind does; without it both halves of this ship green.** **The position itself is `created_at::text`, selected as a SECOND column alongside the typed one and carried through the cursor verbatim: `timestamptz` holds MICROseconds and a JS `Date` holds milliseconds, so rendering a position through a Date floors it and the next page re-reads everything inside the dropped microseconds — a full production walk of a 57k-row brand returned 57,737 rows for 57,622 people (115 repeats, no gaps) before the text column existed. Never build a cursor from the typed `createdAt`.** (#417, v0.52.1, v0.52.2, v0.53.1.)
- **A step outcome a HUMAN states counts exactly like a tracked one, and a "won't" statement counts as nothing anywhere.** The website tracker sees about one conversion in ten (26 of the 29 events ever received are `unmatched`, usually because the person signed up with an address we never emailed) and cannot see an attended meeting or a deal closed on a call at all — 4 booked meetings and 1 closed deal lived as typed notes in the cold-email service, where nothing that computes the funnel reads them. So `POST /orgs/leads/{id}/step-statements` (org-auth; the publishable tracker token is deliberately NOT a door to it — write-only, brand-scoped, meant for a third party's page) lets a caller state a step for the lead row it is already looking at. `{id}` is the `leads_campaigns` row id a list row already carries, so no identity field is re-supplied, nothing is matched, and the statement is attributable to the row's CAMPAIGN, not only to its brand. Three things are load-bearing: (1) `kind:"outcome"` writes a `conversion_events` row tagged `source='manual'` — the ledger every consumer already counts, so a brand's counts move with zero consumer change, while `source` (plus `bySource` on `/internal/brands/:id/conversion-counts`, where `tracker + manual === counts` per key) keeps hand-stated distinguishable from tracker-reported after the fact; restating a step corrects it (dedupe signature `m:<leadCampaignId>:<step>`) instead of counting twice. (2) `kind:"never"` is NOT an outcome, so it lives in `lead_step_disqualifications`, a table NO count reads — the guarantee is structural, not a filter every consumer must remember — and `GET /internal/brands/:id/step-disqualifications` is how a consumer separates a lead DEAD at a step from one still PENDING (a cost-per-acquisition denominator that will never resolve from one that still might). The two are mutually exclusive per step and resolve in the only direction that can be true: an outcome retracts an earlier "never" (people change their mind and buy) and says so; "never" on a step that already happened is a 409. (3) `meeting_attended` is a fifth countable outcome — sales funnels have always carried the step and brand-service prices with a booked-to-attended rate that no event in the fleet could measure — and it is statable BY HAND ONLY: `canonicalizeStepOutcome` accepts it, `canonicalizeConversionEvent` (the tracker's ingest gate) does not, because a page-load tag cannot observe somebody showing up. Do NOT widen the tracker's accepted vocabulary to reach it, and do NOT make a "never" reachable from any count. (#448.)
- **A website VISIT is statable by hand too, and the hand-stated one is suppressed wherever the delivery layer already measured it.** Two of the four sales funnels START at a website visit, and it was the one step of those funnels nobody could state: the panel showed a row it could only read above three it could act on, with no way to correct the first step when the automatic signal missed. That signal is a CLICK measured by the delivery layer (email-gateway), and it misses for the same family of reasons the tracker's identity waterfall misses. So `website_visit` joins `meeting_attended` as a step `canonicalizeStepOutcome` accepts and `canonicalizeConversionEvent` (the tracker's ingest gate) does not — the tracker's vocabulary is unchanged, nothing about what the delivery layer measures or how a click is attributed is touched, and a `never` on the visit lands in `lead_step_disqualifications` where no count reads it, exactly like the five steps that already ship. What is new is that this step is the only one measured BOTH ways, so the two must not be added up: `measuredVisitEventIds` (`src/routes/conversions.ts`) asks email-gateway, at brand scope, which hand-stated visits belong to a lead whose click it already measured, and every outcome read (`/conversion-counts`, `-by-day`, `/converted-leads`, `/converted-lead-emails`) excludes those rows — so `counts.website_visit` is the visits known ONLY by hand, the number a consumer ADDS to its measured click count. A brand with no hand-stated visit costs one extra indexed SELECT and makes NO network call, so every existing brand's reads are byte-identical; a lead with no registered email is never suppressed (the measured signal keys on that email, so it cannot be in the measured set); email-gateway unreachable is a 502, never a guessed count. `GET /orgs/leads/{id}/step-statements` reads a measured visit back as an outcome with `source:"tracker"` and refuses a `never` on it (409), so the panel never invites somebody to state a fact the system already holds and can never show a step state the counts contradict. Do NOT widen the tracker's ingest to reach it, and do NOT make the counts sum the two signals.
- **An outcome a consumer must VALUE and CHART is read one row at a time, carrying WHEN and HOW MUCH — `GET /internal/brands/:id/converted-leads?event=<step>`.** Its sibling `/converted-lead-emails` answers WHO and nothing else, which is enough to intersect with audience membership and enough for nothing else: an outcome read through it has no date (so it can only land in the undated bucket, uncharted and unattributable to a period, which breaks an ROI-over-time curve), no campaign (so only the brand total can move — the per-campaign, per-workflow and per-offer grains cannot attribute it at all) and no value (so a won deal is priced at the brand's AVERAGE lifetime revenue instead of what it was worth). The new read carries all three plus `source`, so features-service can stop projecting declared rates through a lead whose outcome somebody actually observed. **The set is EXACTLY the one `/conversion-counts` and `/conversion-counts-by-day` count** — same brand, same step, same `attributed` filter — so `outcomes.length` equals the total and bucketing `occurredAt` by UTC day reproduces the by-day series, `null` landing in `undated`. That is why the canonical-email join is a LEFT lateral here and an INNER one on `/converted-lead-emails`: that read is a SET of join keys and a lead with no email has none, while dropping the row HERE would silently make two reads disagree about how many outcomes exist. `campaignId` is null on a tracker row by construction (a page-load tag knows the brand and nothing else) and never guessed. Both existing reads are untouched; this is additive.
- **A funnel is ORDERED, so what is known about one step constrains its neighbours — and that order is per FUNNEL, never universal.** The hand-stated statements shipped with two rules between a step and ITSELF and none at all between steps, so `meeting_booked: never` + `meeting_attended: outcome` + `sale: outcome` was reachable, and nobody attends a meeting that was never booked. Two rules now run in opposite directions: a **never** makes every LATER step of that campaign's funnel never (which is what makes the dead-versus-pending distinction hold across a whole funnel rather than one row), and an **outcome** makes every EARLIER one reached (a lead that paid necessarily got through the steps that lead to paying). A step neither rule reaches, and nobody spoke about, stays `pending`. Four things are load-bearing. (1) **WHICH funnel** comes from the CAMPAIGN — campaign-service owns `funnelKey` on the row (`src/lib/campaign-funnel-client.ts`) and it is never inferred from the brand, a sibling campaign or a goal (two funnels answer to the same goal). A funnel that cannot be resolved is an ERROR, never a guess: 502 when campaign-service cannot answer, 409 `funnel_unstated` when the campaign states no funnel — which does mean the panel refuses on the ~106 legacy campaigns carrying a null `funnel_key`, deliberately, because there is no order to read their steps in. (2) The funnelKey→steps mapping lives HERE (`src/lib/funnel-steps.ts`), because brand-service publishes a funnel's steps as DISPLAY LABELS ("Website visit", "Paid client") and something has to translate them into this service's outcome vocabulary; the funnel KEY is what is read from the producer. A funnel's steps here are only statable ones, so `conversation_reply` and `ad_click` are absent — which changes nothing about the order of the rest. (3) **Implication is computed on READ** (`src/lib/step-funnel-state.ts`), never written: no `conversion_events` row and no disqualification row is ever fabricated, so counts are untouched for a lead nobody made a new statement about, and retracting a statement moves everything it implied with it automatically. `origin: "stated" | "implied"` is what tells a reader who said what, and an implied step carries no author, no note and no date because nobody made it. (4) A contradicted "never" is **retracted, never deleted** (migration 0033 `retracted_at`/`retracted_by_step`; every read filters `retracted_at IS NULL`), so the record of what somebody actually stated survives being superseded — `statedState` reads it back even where the funnel concluded otherwise. Precedence per step is: own stated outcome > outcome later on the funnel > own stated never > never earlier on the funnel > pending, i.e. a fact beats a prediction, which is the same-step rule ("an outcome retracts a never") expressed along the funnel. The brand-level `GET /internal/brands/:id/step-disqualifications` applies that order only under `?implied=true` (it needs a campaign-service read per org), and answers `impliedCounts`/`effectiveCounts` alongside the untouched stated `counts`. **Bind any step-list into a raw `sql` template through `sql.param(...)`** — a bare JS array compiles to `ANY(($1, $2, $3)::text[])`, which Postgres rejects with `op ANY/ALL (array) requires array on right side`. **On the wire the funnel's steps are `funnelSteps`, and a step's membership of them is `inFunnel` / `stepIndex` (v0.62.0) — the word "chain" is retired here and fleet-wide, and `tests/unit/funnel-vocabulary.test.ts` fails the build if it returns to a property name or a description in `openapi.json`, or to any file under `src`, `tests`, `scripts` or `drizzle`.** It was this fleet's second name for the same thing (features-service, api-service and all three dashboard apps dropped it first), and this service was the last producer still serving it, which is the only reason the two consumer apps ever read it. Nothing about the DATA moved with the rename — same steps, same order, same semantics — and no alias was left behind: the consumers read both spellings for exactly one deploy and then dropped the old one. The carve-out is the word used for something that genuinely is not a sales funnel (a CALL chain, a CAUSE chain, the SEND chain a lead is handed to), which the guard allows by exact phrase so "sales chain" can never slip through on the back of one.
- **A statement a PERSON made can be WITHDRAWN — `DELETE /orgs/leads/{id}/step-statements/{step}` — and a withdrawal is the ABSENCE of a statement, never a third kind of one.** Somebody states a step on the wrong lead, on the wrong step, or off a reply they misread, and the only correction on offer was stating the opposite thing, which is itself a false statement and one that keeps counting: the outcome stays on the ledger and the cost the customer stated for it stays in their spend, so every cost of acquisition and every return downstream carries money nobody spent for an outcome nobody had. So both stores carry `withdrawn_at`/`withdrawn_by_user_id` (migration 0035) and EVERY read that already filters `retracted_at IS NULL` filters it too — counts, by-day, `/converted-leads`, `/converted-lead-emails`, `/step-costs`, `/step-disqualifications`, the panel read, the measured-visit suppression set and the write path's own contradiction guard. Nothing is deleted: what somebody stated, and the fact they later withdrew it, both stay readable, the same posture supersession already takes. Four things are load-bearing. (1) **`withdrawn_at` and `retracted_at` are DIFFERENT facts and stay apart** — retraction is the funnel resolving a contradiction (an outcome proved the "never" wrong), withdrawal is the author saying it should never have been stated — so withdrawing an OUTCOME un-retracts the "never"s that outcome retracted (`retracted_by_step = <step> AND withdrawn_at IS NULL`, so one withdrawn on its own account is left alone), and restating any withdrawn statement clears the mark through the existing upsert. (2) **Implication re-derives on READ, as it always did**, so a step that only read as reached or as dead because of the withdrawn statement falls back to whatever the remaining statements imply with no extra write — and the response carries those re-derived `steps`, computed by the SAME `loadStepStates` the panel read uses, so a caller never guesses what its withdrawal did and the two surfaces cannot diverge. (3) **Only a statement a PERSON made is withdrawable**: a tracker-reported or delivery-measured outcome is 409 `not_a_statement` (this service does not edit what another system observed) and a step nobody stated is 409 `nothing_stated`, carrying `state`/`origin`/`impliedBy` so an implied step names the statement to withdraw instead — both distinguishable from a 500 by their `code`. (4) **Idempotent**: withdrawing what is already withdrawn is a 200 `alreadyWithdrawn: true` that writes nothing. Purely additive — the write is unchanged and no live caller can observe a difference.
- **A stated `sale` MUST carry `valueCents` (400 otherwise); every other step keeps it optional.** A won deal is the one place in the system where estimating has no excuse: with no value, every downstream money figure — pipeline, ROI, cost per acquisition — falls back to the brand's average lifetime revenue, a number that describes no real customer, and does it silently. The other steps stay optional deliberately, because an unusually large lead is worth stating early, long before it closes. This is a breaking request-contract change for whoever writes statements, so the dashboard must ask for the amount on a sale BEFORE this reaches production — consumer-first, per the deploy-ordering rule. (#450.)
- **Every step statement MUST state what that transition COST THE CUSTOMER (400 `cost_required` otherwise), and that money NEVER enters the platform's cost ledger.** The product sells a sales funnel one step at a time, and the steps the platform does not automate are performed by the customer — they run the meeting, they close the deal — so they are the only one who knows what that leg cost. Without it a funnel's cost of acquisition counts only the leg we billed for and every return displayed for that funnel is too good. `costCents` is required on BOTH kinds: a `never` carries one too, because a meeting that was run and went nowhere cost exactly what it cost. **Absent is a REFUSAL, never a zero, and the column is nullable rather than `NOT NULL DEFAULT 0` for the same reason**: `0` is a stated zero (a legitimate answer — the author chooses what goes in, zero, their time valued however they like, real expenses) and `NULL` is "nobody was ever asked" (every statement made before this shipped, and every tracker-reported outcome — a page-load tag observes a page load and knows nothing about a customer's spend). Defaulting the legacy rows to 0 would fabricate an answer nobody gave and the two could never be told apart again; that is also why the internal read answers `statedCount`/`unstatedCount` beside each total instead of a bare sum. **This money is the CUSTOMER'S**: it is recorded because they told us, never charged to them — no runs-service cost is provisioned/actualized for it, no billing authorize is called, nothing about it appears in the org's spend. The consumer read is `GET /internal/brands/:id/step-costs[?step=]` (one row per live hand statement, outcomes and `never`s alike, with campaign grain), plus `costCents` on each `/internal/brands/:id/converted-leads` row. Its set is deliberately NOT the set `/conversion-counts` counts, and that is not a contradiction because this is MONEY and that is a POPULATION: a hand-stated `website_visit` whose click the delivery layer already measured is suppressed from the counts (one visit, counted once) but kept here (the money was spent either way), while a RETRACTED `never` is excluded exactly as everywhere else, because the outcome that superseded it carries its own cost. Breaking request-contract change for whoever writes statements — the dashboard must ask for the amount before this reaches production, per the consumer-first deploy-ordering rule. (Migration 0034.)
- **Where a lead STANDS is decided here and nowhere else, per campaign, derived on read — `standing` on every `GET /orgs/leads` row and on `GET /orgs/leads/{id}`.** "Is this person still a live prospect" is COMMERCIAL POLICY, and it was decided in three independent places from two different sources with no owner: the dashboard computed it per lead off the reply signals, features-service counted an aggregate for the campaign's stat card, and instantly-service froze a coarse classification at write time that fed both. That split has already produced a customer-visible contradiction (instantly-service#649: a referral read as interest on one surface and not on the other, for months). This service is the only one holding BOTH halves — the delivery evidence it already joins onto the membership row, and the hand-stated step statements it owns — so the policy lives in `src/lib/lead-standing.ts` (pure) and everything else renders it. Five things are load-bearing. (1) **FUNNEL-AWARE, not funnel-agnostic.** `sales_interest` means "reached the step this campaign's funnel is ENTERED by", and that step is per funnel: a visit-led funnel is entered by a CLICK the delivery layer measures, a conversation-led one by a POSITIVE REPLY it classifies, and an ads-led one by an ad click nothing here observes. `FUNNEL_ENTRY` (`src/lib/funnel-steps.ts`) is that catalogue, and it is a different question from `FUNNEL_STEPS[key][0]` — a funnel's first STATABLE step is not always its first step, which is why `sales_meetings_from_conversation` starts its steps at `meeting_booked`. So the same click is `sales_interest` on `form_magnet` and `engaged` on a campaign that prices no visit; the `(lead, campaign)` grain is what lets both be true of one person, and the funnel comes from the CAMPAIGN (campaign-service `funnelKey`) exactly as the step statements' funnel does — never from the brand, never from a goal. The measured 67-click case that forced it: campaign `9e28ba26` sells `visit -> form -> paid`, 67 people clicked through, 0 replies were positive, and the customer's board showed zero cards under Sales interest. (2) **Precedence is evidence strength, and the opt-out is absolute.** unsubscribed (scope or global) > a human statement (an outcome on the funnel, then a `never`, both read through the SAME `resolveStepStates` the panel reads so the two surfaces cannot disagree) > bounced > the funnel's own entry step reached > a reply DISQUALIFICATION > engagement > contacted. A click plus a negative reply on a visit-led funnel is `sales_interest`: reaching the step is a fact about the funnel, a classification is a judgement about a message. Nothing overrides an unsubscribe — not a click, not a stated sale. **A negative reply is NOT a disqualification.** Disqualified means one thing: we realised this person is not our target — the wrong contact, or gone from the role — which is ordinary sales qualification (we sell pears to supermarkets and wrote to somebody in construction). A decline about the offer today is a judgement about the MOMENT: the person is still reachable and the lead is still recyclable, so they read `engaged` with `signal: "negative_reply"`. "They cannot buy" is the same thing. An opt-out is the prospect's OWN act, has its own column, and never shares one with a commercial judgement of ours — which is why `signal` and not `state` is what draws that column. The finer reading is DERIVED BY THE PROVIDER and forwarded through email-gateway's status read as `disqualified` (boolean, OPTIONAL); read that derived answer and never re-derive it from a list of reply kinds this service would then have to keep in lockstep with instantly-service. Absent is a THIRD state — a provider that does not track replies serves no reading, and neither does an older payload — and it is neither a yes nor a no: a negative reply with no disqualification reading answers `unresolved` / `reply_disqualification_unknown`, never a default in either direction. The merge across providers ORs only over the providers that ANSWERED (`mergeDisqualified`), so "nobody can tell us" survives a provider that never serves the field. (3) **NOTHING is fabricated and NOTHING is defaulted.** A row that was never served is `not_contacted` and is judged no further; an unscoped read (delivery layer never asked), an unresolvable funnel, and an unreadable statement each answer `state: "unresolved"` with the `reason` on the wire. `reachedEntryStep` is `null` — never `false` — on an ads-led funnel, because "no" would be a claim this service cannot make. A resolver failure downgrades ONE field, never the read: a 57k-row walk is not failed over a derived value. (4) **Derived on READ, never stored.** Retracting or withdrawing a statement moves the standing with it, with no write and no backfill, exactly as the panel's step states already work. (5) **Resolved ONCE per response.** `createLeadStandingResolver` reads the org's campaign -> funnel map in a single campaign-service call reused by every chunk, and folds in the measured visit from the delivery overlay the row ALREADY carries (a click IS the automatic half of `website_visit`) rather than making a second email-gateway call. The statements are two indexed reads per chunk, batched. Purely additive: every raw delivery fact stays on the row unchanged — they are what let the policy change later — and a consumer that ignores `standing` keeps working. Do NOT re-derive this in a consumer, and do NOT let a consumer add a signal of its own to it; that is the three-implementations split this closes. (#472.)
- **A caller holding one lead's identity reads that lead ALONE — `GET /orgs/leads/{id}`, keyed on the `id` a list row already carries, answering `{ leadDetail }`.** A surface with a table plus a detail panel used to take the FULL projection for the whole brand so that one panel could work: ~57k rows and >100 MB on one production brand, in a tab that polls it every 30s, and the same read server-side on the public report page. `limit` does not help that shape — the table wants every row (it groups by lifecycle state) and only the panel wants depth. The detail read looks the row up by its own `id` with `org_id` IN the predicate (a foreign row is indistinguishable from an absent one, never a check afterwards) and no dedup and no lifecycle filter (the caller is naming a row it was already shown, not asking which of a person's rows wins). `brandId`/`campaignId` mean exactly what they mean on the list — which scope the delivery overlay answers for, campaign resolved to the whole identity — and a `brandId` the row is not part of is a 404, not a leak. **Both routes serialize through the ONE `serializeLeadItem` in `src/routes/leads.ts`; keep it that way** — a field on the list and not the detail is a panel that changes shape depending on how it was loaded, and `tests/unit/leads-detail-route.test.ts` asserts the exact key set. Do NOT re-solve this as a filter on the list route returning a one-element list: a consumer asking for one record should not be constructing a list query, and the response shape should say what it is. (#3416.)
- **Raw-`sql` route tests that mock `db.execute` do NOT exercise postgres.js `Bind` — a handler that binds an unserializable param (a raw `Date`) still ships GREEN.** The plain `vi.fn()` mock returns rows without ever encoding params, so the Bind-time throw above never fires in tests. Any test asserting a raw-`sql` write handler returns 200 MUST also assert the compiled params are Bind-serializable (no `Date` instance) — see the `assertBindable` Bind-faithful mock in `tests/unit/conversions-routes.test.ts`, which throws on a raw `Date` exactly like prod. Without it a 100%-broken handler passes CI. (#370.)

## `businessLanguages` is CARRIED, never derived here

human-service derives, per person, the language(s) they plausibly conduct business in and exposes them as `businessLanguages` (ISO 639-1 lowercase, ORDERED most-plausible-first, empty array = no usable signal). lead-service sits between that producer and content-generation-service, which writes each cold email in the recipient's language rather than always in English. This repo's only job in that sequence is to carry the value through intact.

- **Never derive, infer or guess a language here** — not from `city`/`state`/`country`, not from the name, not from the organization. human-service owns the derivation and the vocabulary; a second implementation would drift from it silently. `tests/unit/lead-business-languages.test.ts` guards this.
- **Order is the contract.** The end consumer selects by position (index 0 = most plausible), so the column is a Postgres `text[]` precisely because it preserves insertion order. Never sort it, de-duplicate it into a set, or normalize it.
- **Three states, all distinct, none of them a guess**: `NULL` = the lead predates the field being carried; `{}` = the producer had no usable signal; `{en}` = known to be English. Do not collapse `{}` into `NULL`, and never substitute a default for either.
- **Nothing is backfilled.** The column is only ever written from real producer data, via `PERSON_FIELDS` in `src/lib/leads-registry.ts` — presence in that list IS the write path (`pickPersonFields` copies the key straight off the neutral `Person`). Added 2026-08-26 alongside human-service v0.40.0.
- The neutral `Person` (`src/lib/people-client.ts`) is a pass-through cast of human-service's response, so the field arrives populated with no mapping code; `src/lib/lead-shape.ts` emits it on both the single and batch `FullLead` paths.

## Boot — the port opens BEFORE migrations, and traffic is gated until they finish

- **`app.listen()` runs FIRST; `migrate()` runs behind it.** This was learned on Neon, whose computes suspended after inactivity: a deploy landing on a cold compute spent its whole startup budget on the first connection, so the port never opened inside Railway's 30s healthcheck window (`1/1 replicas never became healthy!`, with no application output at all — not even "Migrations complete" — because the stall happens before any logging), or the connection was refused mid-resume and the old `.catch(process.exit(1))` turned it into a restart loop. Neon and Railway are both gone; the failure SHAPE is not. Any moment the database is not ready to accept a connection right now — the Postgres container restarting, the box rebooting, a deploy restarting things underneath — reproduces it exactly, and `deploy.sh`'s health check will roll the release back for a port that never opened. The failure has nothing to do with the code being deployed, which is what makes it expensive: it reads as a flaky deploy, you retry, the DB is up by then, it passes. Do NOT move migrations back in front of `listen()`, and do NOT add pre-listen startup work (`registerProviders()` used to be there too — it now runs after readiness, non-fatal, because publishing metadata to key-service is not schema and a key-service outage must not hold the service at 503).
- **Opening the port early is only safe because `requireBootReady` (`src/middleware/readiness.ts`) 503s every route until migrations complete.** The service must never serve a request against a schema its code does not expect. `/health` is mounted BEFORE the gate; everything else after it. Keep that order when adding routers.
- **`/health` is boot-state-aware and must NOT ping the DB while `starting`.** Three states (`src/lib/boot-state.ts`): `starting` → 200 `{status:"starting",migrations:"pending"}` with no DB access (a database not yet accepting connections would otherwise fail the ping and take the deploy down — the exact bug, originally a Neon compute mid-resume); `ready` → the usual `SELECT 1` ping; `failed` → 503 naming the migration error, so the deploy's health check fails loudly and `deploy.sh` rolls back to the previous build. On migration failure the process deliberately stays ALIVE rather than `process.exit(1)` — exiting produces a restart loop that shreds the logs carrying the reason.
- **Migration retry is connect-phase ONLY (`withConnectRetry`, `src/lib/db-retry.ts`).** A rejected connection never dispatched a statement, so retrying it cannot half-apply a migration; a real migration error (bad SQL, failed constraint) is NOT retried and surfaces on the first throw. Budget ~65s, front-loaded (250ms → 8s) — sized to cover a Neon resume many times over when it was written, and it comfortably covers a Postgres container coming back up. Transient detection walks `cause` chains and `AggregateError.errors` (Node-20 happy-eyeballs produces one sub-error per candidate address) and matches driver codes, SQLSTATE class 08, `57P03` (`cannot_connect_now` — Neon returned it while resuming, and Postgres returns it while still starting up), and the code-less pool-acquire message `timeout exceeded when trying to connect`.
- **Do NOT "fix" cold starts with postgres.js connection options.** `connect_timeout: 30` is already the postgres.js default (`postgres/src/index.js`), so setting it is a no-op; `idle_timeout` defaults to `null` (idle connections are never closed), so setting a value makes them close and buys a fresh TCP+TLS handshake on the next request — that advice is correct for node-postgres, whose default really is an aggressive 10s teardown, and was mis-transplanted. Both were tried and reverted in brand-service#389. The one connection-layer setting kept here is `net.setDefaultAutoSelectFamilyAttemptTimeout(5_000)` in `src/db/index.ts`, which widens Node 20's 250ms per-candidate happy-eyeballs budget so the first connection to a database that is not yet ready is not aborted before it is answered.
- **A test file that `vi.mock`s `src/db/index.js` MUST `vi.resetModules()` between cases.** Without it the mocked module registry leaks into LATER test files in the same worker, and the symptom lands nowhere near the cause: `tests/unit/stats-persona-attribution.test.ts` hung to a 5s timeout, deterministically, because `health.test.ts` ran before it without the reset. Import the boot-state singleton through the same fresh registry as the route under test (a static top-level import binds to a different instance after `resetModules` and silently stops driving it) — see `tests/unit/health.test.ts`.

## Outbound-call resilience & route error handling

- **ALL outbound calls to runs-service go through `fetchWithRetry` (`src/lib/fetch-retry.ts`), never raw `fetch`.** runs-service used to sit behind Neon scale-to-zero, so the first call after an idle suspend landed mid-wake (~1-7s resume) and aborted the old raw `fetch(..., { signal: AbortSignal.timeout(5_000) })` with a `TimeoutError`/socket-reset. Scale-to-zero is gone, the failure is not: a sibling that is restarting, redeploying, or coming back with the box still refuses or resets the first connection the same way. `runs-client.ts` + `trace-event.ts` now use `fetchWithRetry` (connect-phase retry on `ECONNRESET`/`ECONNREFUSED` — write-safe, request never reached the server) + a 30s timeout (fleet norm; 5s was the outlier that couldn't fit a slow first connect). Any NEW runs-client function (or any client to a sibling service on a fail-loud path) must use `fetchWithRetry`, not raw `fetch`. (#390, v0.44.1.)
- **An `async` Express route handler's throw does NOT become a 500 automatically (Express 4) — it rejects the handler's promise, which Express ignores → `unhandledRejection` + the caller's socket HANGS with no response.** So any `await` in a route handler that can throw MUST be inside a `try` that `return res.status(5xx)`s. The trap: work done BEFORE the main `try` block (idempotency lookup, in-flight guard, `createRun`) is unguarded — a runs-service outage there escaped as an unhandled rejection instead of a clean 500. `POST /orgs/buffer/next` wraps its entire pre-serve block. When adding pre-`try` setup awaits to a route, extend the guard. Route tests must assert 500-on-throw with NO error middleware mounted (Express 4 wouldn't forward the async rejection to it anyway) — see `tests/unit/buffer-route.test.ts`. (#390, v0.44.1.)

## API Design Rules

- **Minimal request body.** Everything that workflow-service auto-injects as headers (`x-org-id`, `x-user-id`, `x-run-id`, `x-campaign-id`, `x-brand-id`, `x-workflow-slug`, `x-feature-slug`) MUST be read from headers, never duplicated in the body.
- **No `.default()` on Zod fields.** If a field is needed, make it required. A missing field is a 400, not a silent default.
- **No optional "convenience" fields.** If the service can fetch data internally (campaign context from campaign-service, brand fields from brand-service), do NOT accept it as a body parameter. Fetch it yourself. **This extends to identity HEADERS, not just body fields: a header carrying a producer-owned attribute that is *derivable* from an entity already identified by another header must be fetched, not required.** The `goal` (signup|meetingBooked|purchase) is a brand attribute (brand-service `brands.currentGoal`), derivable from `x-brand-id` via `GET /internal/brands/:brandId/runtime-context` — so lead-service fetches it inside buffer/next, never requires `x-goal` (v0.25). Carve-out: headers that ARE the request's identity (`x-org-id`, `x-campaign-id`, `x-brand-id`, `x-run-id`, `x-audience-id`) stay headers — they name *which* entity, they are not derivable attributes OF it.
- **Audience selection is campaign-owned — lead-service NEVER re-ranks/re-selects.** campaign-service decides the priority audience per run (`internal.ts` → features persona-stats) and propagates it as `x-audience-id` to every downstream DAG node. `buffer/next` serves the audience named by `x-audience-id` (`req.audienceId`) directly; no `x-audience-id` ⟹ clean `found:false` (campaign selected none). Do NOT re-introduce a features-service `persona-stats`/`getTopAudienceId` call in lead-service — that duplicated, divergent selection let an uncommitted audience be picked and 422 at serve-next (v0.26.1 removed it). Serveability (audience has a committed provider) is enforced upstream in human-service; lead-service treats serve-next 422 "no committed provider" as `found:false` (reason `audience_not_serveable`), never a 500.
- **Every empty serve NAMES why it is empty, and exactly ONE name means a population ran out.** `POST /orgs/buffer/next` answering `{ found: false }` in silence made five unrelated situations byte-identical on the wire, and the caller acts on one of them irreversibly: campaign-service stops the campaign, and funding a channel deliberately never revives a campaign stopped for exhaustion. So `found:false` always carries a `reason` (`src/lib/serve-reasons.ts` owns the vocabulary — the Zod enum reads `SERVE_EMPTY_REASONS` from it, so the published contract cannot drift from what the serve path returns). Only `audience_exhausted` is evidence about a population: human-service walked the audience this service was told to serve and reported nobody left. `no_audience` (no `x-audience-id`, so this service — which never picks audiences — looked at nobody), `serve_timed_out` (the budget expired mid-look), `audience_not_serveable` and `credit_insufficient` all state that no exhaustion was observed. A consumer decides "may outreach stop?" by testing `reason === "audience_exhausted"`, never by excluding known-benign values, so a reason added later defaults to not-exhaustion. The `no_audience` branch is NOT a bug to fix by picking an audience here — see the campaign-owned-selection rule above; it is a bug to report as exhaustion. Cost: brand `75d7e3e8`'s second cold-email channel (campaign `4769db14`, 2026-08-20 10:08:10) asked for the first time, got no `x-audience-id`, returned in 26ms without one network call, and was stopped `audience_exhausted` at 10:08:11 — while its sibling campaign served 109 leads for the same brand, same four audiences, the same day. (#439.)
- **`pullNext` drains the already-paid pool BEFORE asking human-service for anyone new.** A serve is billed (apollo/apify enrichment) and suppressed for three months in human-service the instant it happens, so a failure at ANY step after the serve — email generation, the vendor push, anything — strands a prospect the brand paid for and can never be offered again: `serveNext` correctly answers "someone NEW", and the suppression it consults is a PRE-payment guard that must not be relaxed (it is what stops us re-buying a person we already own). The gap was on this side, and so is the fix (`src/lib/retry-pool.ts`): this campaign's own `status='served'`, `sent_at IS NULL` rows, oldest serve first, bounded to `RETRY_CANDIDATE_BATCH_SIZE`, resolved by ONE batched campaign-scoped email-gateway `/orgs/status` call. Both flags decide, not one: `contacted` (broadcast side = pushed to the vendor, i.e. queued) false ⟹ re-serve now; contacted-but-not-`sent` ⟹ the vendor legitimately holds it inside its business-hours window, so wait, bounded by a **5-day** TTL measured from our own `served_at` (the status response carries booleans and no timestamps) — past it the vendor lost it, re-serve. Five and not three because a lead queued Friday evening leaves Monday morning and a bank holiday pushes that past three days, and the error is asymmetric: stranding a lead is recoverable, a second email to a human is not. `sent` ⟹ `sent_at` is written and that person is never returned and never re-queried again — that marker is the only thing keeping the gateway call small as a campaign ages. The winner is taken by a conditional `UPDATE ... RETURNING` on `retry_claimed_at` (an hour-long lease, re-pointing the row's run ids at the claiming run), so two concurrent pulls cannot hand the same person to two runs and a claim that fails downstream is retryable the same day; the lease also doubles as the queue position, so a repeatedly-failing person sorts to the back instead of blocking the head. **The claim does NOT write `status='claimed'`** even though that value exists in `LEAD_LIFECYCLE_STATUSES` and nothing else writes it: the delivery overlay and the dedup winner ordering both key on `status='served'`, so demoting a row that WAS served would silently blank its engagement in `GET /orgs/leads`. email-gateway unreachable is FAIL-CLOSED — fall through to `serveNext`, which merely costs money, rather than guess and send a second email. Empty pool ⟹ one extra indexed SELECT and then byte-identical behaviour. Do NOT turn any of this into a cron or a sweep: it belongs on the serve path, which is the only place that knows a person is about to be handed to a workflow. - **What we owe a prospect NEXT is stored per (lead, campaign), and exactly one worker may act on it — `followup_due_at` + a claim lease on `leads_campaigns` (migration 0036, `src/lib/followup-queue.ts`).** Once somebody shows a sales interest we owe them an answer now and, if they go quiet, further answers at growing intervals, indefinitely; nothing recorded that debt, so a worker wanting to answer the next person due had nothing to ask. Six things are load-bearing. (1) **The claim is the SAME conditional `UPDATE ... RETURNING` shape the paid-pool retry uses (0030), not a second concurrency mechanism** — several replies land in the same instant and a read-then-write race would send a second email to a human, which is the one failure here that cannot be taken back; the lease EXPIRES (an hour) so a worker dying mid-answer strands nobody. `POST /orgs/campaigns/{campaignId}/followups/claim-next` returns at most one person, exactly once. (2) **The interval is the WORKER's choice, stored, never computed here.** A prospect who writes "recontact me in January" must be honoured, so the next due date arrives as data on `POST /orgs/leads/{id}/followups`; this service only BOUNDS it (never in the past beyond a 5-minute clock-skew tolerance, never further out than a year) and REFUSES outside those bounds with the range in the body — a clamp would answer a request nobody made and the caller would never learn its date was wrong. There is deliberately **no cap on the number of follow-ups**: `followup_count` is recorded and read by nothing that gates, because the growing intervals are the limit. (3) **Three stops, none of them guessed.** Opted out — read from email-gateway at claim time and their schedule cleared for good; a booked meeting on record — `meeting_booked`, `meeting_attended` or `sale`, live (non-withdrawn) rows of the conversion ledger, hand-stated or tracker-reported, the last two because they entail the booking; answered again — whoever OBSERVES the reply stops the schedule (`kind:"stopped"`, reason stated) and qualification re-decides with a later `kind:"scheduled"`. That third stop is a statement, not a derivation: reply RECENCY is not something this service can see (the delivery layer serves `firstRepliedAt` and no later one), and inventing a heuristic for it would be exactly the fabrication the standing rules refuse. A stop is therefore NOT a tombstone. (4) **Oldest-due-first**, so a burst of fresh replies cannot starve somebody owed an answer since last week. (5) **email-gateway unreachable is a 502, never a claim** — a wasted poll is recoverable, an email to somebody who asked us to stop is not; there is no fallback branch in the claim path at all. (6) **The scope is the campaign id NAMED, not its identity family** — the family rule governs reads that TOTAL a population, while this hands out a single row whose due date a worker wrote naming that exact campaign. `status` is untouched (a served row stays `served`), so the delivery overlay and the read paths' winner ordering are unchanged, and the concurrency guarantee is proven against a REAL Postgres (`tests/integration/followup-queue-sql.test.ts`, eight workers racing one row) because a mocked database cannot fail the way the real one does.
- **Idempotency is internal.** Use `x-run-id` as the idempotency key. Never expose idempotency keys in the API surface.
